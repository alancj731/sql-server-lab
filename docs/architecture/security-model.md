# Security model

## Principles

1. **No arbitrary execution.** No endpoint accepts SQL, PowerShell, Bicep/ARM, resource IDs, or shell commands.
   Every browser action maps to a fixed command (`start`, `deallocate`, `delete`, …) that enqueues an allow-listed
   job type. Job input is validated, serialized data — never code.
2. **Ownership everywhere.** Every lab/job/audit lookup is filtered by owner (admins excepted). Another user's lab is
   reported as **404**, so existence is not disclosed.
3. **Secrets stay server-side.** VM and SQL secrets are generated by `ISecretProvider` (Key Vault in Azure) and are
   never returned by the API, written to logs, or stored in audit records. `Redactor` masks password, key, token,
   and SAS patterns in any error text before it is persisted or returned.
4. **Destructive operations are confirmed and audited.** Deletion requires the exact lab name in the request body
   (validated server-side). Patch installation (Milestone 9) will require the admin role and typed confirmation.
5. **Audit is append-only.** `ControlDbContext` rejects updates and deletes of `AuditEvent` rows.

## Authentication

| Mode | Where | Behaviour |
| --- | --- | --- |
| `Development` | Local and tests only | `X-Dev-User` header (or `dev_user` query on `/hubs`) or a configured default user. Startup **refuses** this mode outside the `Development`/`Testing` environments. |
| `Entra` | Hosted | JWT bearer validation (authority + audience). Angular authorization-code + PKCE via MSAL arrives in Milestone 3. User ID is the `oid` claim; admin is the `LabAdmin` app role. |

## HTTP hardening (implemented)

- RFC 9457 problem details; unexpected errors return a generic message plus a correlation ID — no stack traces.
- Security headers: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  restrictive CSP and `Cache-Control: no-store` on API responses; HSTS + HTTPS redirect outside development.
- Per-user fixed-window rate limit on mutating endpoints (`RateLimiting:MutationsPerMinute`).
- Input validation: lab name regex, region allow-list, TTL/extension bounds, typed delete confirmation.
- Per-user active lab limit (`LabLimits:MaxActiveLabsPerUser`), TTL with 24 h absolute cap, automatic expiry.
- Configuration validated at startup (`ValidateOnStart`).

## Azure (implemented in Milestone 3)

| Control | Implementation |
| --- | --- |
| No public lab access | Lab NICs have no public IP (asserted by a unit test on the compiled template and by `smoke-lab.sh`). The `snet-labs` NSG allows TCP 1433 only from `snet-apps`, denies 22/3389/5985/5986 and all Internet inbound. |
| Least-privilege Azure role | The app identity holds the custom `SQL Lab Operator (<env>)` role (VM, disk, NIC, deployments, resource-group lifecycle, subnet join) instead of Contributor. Every call is preceded by server-side validation that the target resource group matches `rg-sqllab-{name}-{8 hex}`; the platform resource group can never match. |
| Control database | Azure SQL with Entra-only authentication and public network access disabled (private endpoint). The migrator identity is the SQL admin and runs only in the migration job; the app identity is a database user with `db_datareader`/`db_datawriter`. No SQL passwords exist for the control plane. |
| Lab secrets | VM admin, SQL `sa`, and SQL lab-login passwords are generated in the worker (24 chars, complexity-checked, connection-string safe), stored in Key Vault (RBAC, app identity = Secrets Officer), passed to ARM only as `securestring` parameters, and deleted + purged when the lab is deleted. The first-boot setup script receives them via `customData` (readable only by root on the VM), uses `sa` once to create the lab login, then disables `sa`. |
| Lab VMs | Ubuntu 22.04 (Trusted Launch, secure boot, vTPM) with SQL Server 2022 Developer Edition installed from Microsoft's signed apt repository on first boot. SSH is not reachable (no public IP; NSG denies 22). |
| Lab SQL connections | Over the private VNet with `Encrypt=Mandatory`; `TrustServerCertificate=true` because lab VMs use SQL Server's self-signed certificate and are unreachable from outside the VNet. |
| User sign-in | Entra authorization code + PKCE (MSAL, redirect flow) in the SPA; JWT validation (issuer, audience = API app) in the API; `LabAdmin` app role; SignalR uses `access_token` on the hub path only. `/config.json` exposes only tenant/client IDs and the scope. |
| Browser hardening | The SPA is served by the API (single origin, no CORS) with a strict CSP: scripts from self only, connections to self and `login.microsoftonline.com`. |
| Cost guardrails | Per-user lab limit, TTL + expiry, orphan reconciler, monthly budget alert. |

## Open items (tracked for Milestone 10 threat model)

- SignalR access tokens in query strings must be excluded from request logs in hosted environments.
- Rate limiting is per instance; a distributed limiter is needed when the API scales out (max 2 replicas today).
- Key Vault uses RBAC with public network access; a private endpoint is a hardening option.
- Resource-group naming is enforced in code, not by Azure Policy; a deny policy for `rg-sqllab-*` without required tags would add defence in depth.
